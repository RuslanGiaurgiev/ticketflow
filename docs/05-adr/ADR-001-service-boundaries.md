# ADR-001. Шесть сервисов, у каждого своя база

**Статус:** принято · **Дата:** 2026-10-28

## Контекст

Нужно решить, на какие сервисы делить систему и как они делят данные. Требования, влияющие на решение:
- при старте продаж популярного концерта нагрузка на проверку мест в сотни раз выше обычной, а на остальное — нет;
- деньги проходят через внешнего провайдера, к этой части особые требования по безопасности и аудиту;
- выпуск билетов и уведомления можно задержать на секунды, но нельзя потерять;
- команда из 3–4 человек, и каждый должен работать над своей частью без постоянных конфликтов.

## Варианты

1. **Монолит с одной БД.** Покупка — одна ACID-транзакция. Но внешний платёж в неё всё равно не входит, нельзя масштабировать только горячую часть, а падение почты или провайдера роняет всё.
2. **Микросервисы с общей БД.** Проще писать, но сервисы связаны через схему: изменение таблицы ломает соседей, нет изоляции нагрузки, не понятно, кто владелец данных.
3. **Микросервисы по бизнес-возможностям, база на сервис.** Catalog, Inventory, Order, Payment, Ticketing, Notification.
4. **Мелкая нарезка** (отдельно Venue, Pricing, Seat Map, QR, Check-in…). Больше сервисов, чем людей в команде, много сетевых вызовов ради одной операции.

## Решение

Вариант 3. Границы проведены по инвариантам и профилю нагрузки:
- **Inventory** владеет единственным инвариантом «одно место — один покупатель» и горячей нагрузкой;
- **Payment** изолирует деньги и внешнего провайдера;
- **Order** знает процесс целиком и ничего больше;
- **Ticketing** живёт после покупки и обслуживает вход;
- **Catalog** — справочник, почти только чтение;
- **Notification** — побочный эффект, который не должен тормозить покупку.

Каждый сервис владеет своей схемой в PostgreSQL. Чужие таблицы читать запрещено — только API или события. Для учебного стенда допускается **один инстанс PostgreSQL с отдельными базами и отдельными пользователями** на сервис: изоляция владения сохраняется, а инфраструктура проще.

## Последствия

**Плюсы**
- Inventory масштабируется отдельно, падение почты не мешает продажам.
- Каждый участник команды отвечает за 1–2 сервиса.
- Можно заменить провайдера, тронув только Payment.

**Минусы**
- Нет общей транзакции на покупку → нужна сага (ADR-002) и надёжная доставка событий (ADR-003).
- Данные дублируются: Inventory хранит цены мест на момент публикации, Notification — копию данных заказа из событий. Это осознанно: копия — снимок на момент события, а не живая ссылка.
- Нужна распределённая трассировка (`correlationId` = `orderId` во всех логах и сообщениях).
