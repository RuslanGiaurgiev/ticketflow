# ADR-005. Идемпотентность на каждой границе

**Статус:** принято · **Дата:** 2026-10-28

## Контекст

В распределённой системе повтор — нормальная ситуация, а не ошибка:
- покупатель дважды нажал «Купить» или браузер повторил запрос после таймаута;
- Order не дождался ответа от Payment и повторил вызов, хотя платёж уже создан;
- провайдер присылает один и тот же вебхук несколько раз (так он гарантирует доставку);
- Kafka повторно доставляет сообщение после падения консьюмера (ADR-003).

Без защиты каждый из этих повторов даёт дубль: второй заказ, второе списание денег, второй билет на то же место.

## Варианты

1. **Exactly-once на уровне транспорта.** Не существует end-to-end, особенно с внешним провайдером.
2. **Не повторять ничего.** Тогда таймаут = потеря: непонятно, прошёл платёж или нет.
3. **Повторять всё, а каждого получателя сделать идемпотентным** — повтор с тем же ключом даёт тот же результат без новых эффектов.

## Решение

Вариант 3. У каждой операции, которая меняет состояние, есть **ключ идемпотентности**, закреплённый **уникальным индексом в БД** (а не проверкой в коде — она не защищает от гонки двух одновременных запросов).

| Граница | Ключ | Повтор возвращает |
|---|---|---|
| Клиент → `POST /orders` | `Idempotency-Key` (UUID, генерирует клиент) | Тот же заказ, 200. Другое тело с тем же ключом → 422 |
| Order → `POST /holds` | `orderId` | Тот же холд |
| Order → `POST /payments` | `orderId` | Тот же платёж, тот же `confirmationUrl` |
| Payment → провайдер | `Idempotence-Key = orderId` (создание), `= paymentId` (возврат) | Провайдер вернёт уже созданный объект |
| Провайдер → вебхук | `providerEventId` | 200, без эффектов |
| Kafka → любой консьюмер | `messageId` (таблица inbox) | Пропуск |
| Переход саги | Текущий статус в `WHERE` | 0 обновлённых строк → пропуск |
| `IssueTickets` | `orderId` + индекс `(event_id, seat_id)` | Те же билеты |

Правила ретраев: экспоненциальная задержка с джиттером (100 мс → 200 → 400 … до 30 с), не больше 5 попыток для синхронных вызовов. Синхронные вызовы Order → Inventory/Payment защищены circuit breaker: если Payment недоступен, покупатель сразу получает 503 и может повторить с тем же ключом.

## Последствия

**Плюсы**
- Любой участник может безопасно повторять — это база для всех сценариев восстановления в саге.
- Поведение предсказуемо и проверяется простым тестом: «отправь дважды → эффект один».

**Минусы**
- В каждой таблице с эффектами нужен уникальный ключ, плюс таблицы inbox и `provider_webhook_log`.
- Ключи `Idempotency-Key` хранятся 24 часа, потом удаляются; повтор через сутки создаст новый заказ (приемлемо).
- Разработчикам нужна дисциплина: новый обработчик без ключа идемпотентности не проходит code review.
