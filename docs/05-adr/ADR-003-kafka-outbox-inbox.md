# ADR-003. Kafka + Transactional Outbox + Inbox

**Статус:** принято · **Дата:** 2026-10-28

## Контекст

Сервисы обмениваются командами и событиями саги (ADR-002). Классическая ошибка — **dual write**: сервис коммитит изменение в БД, а потом отправляет сообщение в брокер. Если процесс упадёт между этими двумя действиями, данные изменились, а событие потеряно (оплата прошла, а Order об этом не узнал). Обратный порядок — отправить, потом коммитить — даёт событие о том, чего не было.

Кроме того, любой брокер при сбоях может доставить сообщение повторно. Нужно гарантировать «ничего не потеряно и ничего не задвоено» по эффекту.

## Варианты брокера

| | RabbitMQ | Kafka |
|---|---|---|
| Хранение | Удаляет после подтверждения | Хранит лог N дней, можно перечитать |
| Порядок | Внутри очереди, ломается при нескольких консьюмерах | Внутри партиции, ключ = `orderId` → все сообщения заказа по порядку |
| Повторное чтение после бага | Нет | Да, сдвинуть offset |
| Сложность запуска | Ниже | Выше (но есть KRaft без ZooKeeper) |

## Варианты надёжной публикации

1. Отправлять в брокер после коммита и надеяться — **теряет события**.
2. Kafka-транзакции — покрывают только Kafka, не PostgreSQL.
3. **Transactional Outbox**: событие пишется в таблицу `outbox` в той же транзакции, что и бизнес-данные. Отдельный relay читает `outbox` и шлёт в Kafka.

## Решение

- Брокер — **Kafka** (KRaft, 3 брокера, `acks=all`, `min.insync.replicas=2`, идемпотентный продюсер). Ключ сообщения — `orderId`, поэтому события одного заказа приходят по порядку.
- Публикация — **Transactional Outbox** во всех сервисах, которые что-то публикуют. Relay — простой поллер (`SELECT ... FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED`) раз в 200 мс. В перспективе можно заменить на Debezium CDC.
- Приём — **Inbox**: консьюмер в той же транзакции, что и обработка, делает `INSERT INTO inbox(message_id)`. Уникальный ключ отсекает дубль. Offset коммитится после коммита БД.
- Сообщения, которые не удалось обработать за 5 попыток (например, невалидная схема), уходят в `<topic>.dlq` с алертом.

Итог — **at-least-once доставка + идемпотентная обработка = effectively-once по эффекту**.

## Последствия

**Плюсы**
- Событие публикуется тогда и только тогда, когда закоммичены данные.
- Если Kafka лежит, сервисы продолжают работать — события копятся в outbox.
- Можно перечитать топик после исправления бага в консьюмере.

**Минусы**
- Задержка доставки до ~200–500 мс из-за поллинга. Для саги покупки это незаметно.
- В каждом сервисе две служебные таблицы и фоновый relay; их нужно чистить (удалять отправленное старше 7 дней).
- Kafka тяжелее RabbitMQ в развёртывании. Для локального стенда — один брокер в docker-compose.
